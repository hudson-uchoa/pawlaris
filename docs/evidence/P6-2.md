# P6-2 — Tracking and the point store

Every step below is OWNER and requires a physical Android 14+ phone.
No step has been executed and no device result is recorded here. When
executing a step, record its date, phone model, Android version and build
under it. Use `<serial>` for adb commands and never record a real serial.
Keep screenshots, recordings and database copies in the ignored local
directory `docs/evidence/media/`. Record counts, sequence numbers, timing
gaps and tracking mode only; never paste coordinates or route data here.

- [ ] OWNER — Identify the physical phone and build. Run
  `adb -s <serial> shell getprop ro.product.model` and
  `adb -s <serial> shell getprop ro.build.version.release`.
  Install a development build with the P6-1 native modules and manifest
  changes plus this task's JavaScript. Do not use an emulator or Expo Go.
- [ ] OWNER — In Android's Pawlaris permission settings, allow precise
  location only while using the app. Leave background location ungranted.
  Complete the notification and battery rationale steps. Record the
  permission choices and battery-optimization setting. Keep Pawlaris
  visible before starting the walk.
- [ ] OWNER — Start a walk for a non-archived dog. The live screen is a
  later task, so if its start control is unavailable, use an owner-local
  development harness with the real signed-in app runtime. Import
  `createTracker`, `createPointStore`, `Kv` and `expo-location` in that
  harness and retain the tracker instance for cleanup. With that runtime
  bound as `app`, construct it as follows; do not commit the harness:

  ```ts
  const tracker = createTracker({
    driver: app.db,
    kv: new Kv(app.db),
    clock: app.clock,
    points: createPointStore(app.db),
    mutations: app.mutations,
    location: Location,
    async requestBackgroundLocation() { return false; },
  });
  const dog = Object.values(app.store.getState().pets).find(
    (pet) => pet.species === 'dog' && pet.archived_at === null,
  );
  if (dog === undefined) throw new Error('A non-archived dog is required');
  await tracker.start(dog.id);
  ```

  Do not print the returned walk or any GPS fix. This harness refuses the
  optional background grant, representing the ladder's decline choice.
  If startup fails, record the error without coordinates and stop the
  measurement; do not claim foreground or service recording succeeded.
- [ ] OWNER — Open Android Studio's App Inspection, Database Inspector
  for the connected development app, and select `pawlaris.db`. Use its
  SQL query console while the app is running. Run this query after the
  first fixes arrive; record its baseline count, sequence and mode:

  ```sql
  SELECT w.tracking_mode, COUNT(p.seq) AS point_count,
         COALESCE(MAX(p.seq), 0) AS last_seq
  FROM local_walk AS w
  LEFT JOIN walk_point AS p ON p.walk_id = w.id
  GROUP BY w.id, w.tracking_mode;
  ```

  Record whether the foreground-service notification is visible. Expected
  normal mode is `service` with foreground permission alone. If mode is
  `foreground`, record that fact and whether step 3b was offered; retain
  that mode throughout this measurement. Never select `lat`, `lon`, all
  columns or the route, and never export the full database into Git.
- [ ] OWNER — Close/detach the inspector and debugger so they do not keep
  the app active. Record the baseline `last_seq` as `<before-lock-seq>`.
  Lock the phone with the hardware button and move outdoors for three
  minutes, timed independently. Keep the screen locked throughout; do
  not pause the walk. Record the actual duration, without location details.
- [ ] OWNER — Unlock after three minutes and return to Pawlaris. Reattach
  the inspector promptly and rerun the count query. Record the new count,
  final sequence as `<after-unlock-seq>`, and tracking mode. Record whether
  fixes continued arriving while locked, including any interruption or
  mode change. An increase only after unlocking is not proof of continuous
  locked-screen delivery; inspect the gaps in the following step.
- [ ] OWNER — Read gaps from the same database without coordinates.
  Replace both sequence placeholders below with the observed integers.
  The first query lists each gap, including the gap across the lock
  boundary; the second reports their count, average and maximum:

  ```sql
  WITH gaps AS (
    SELECT p.seq,
           (p.t - LAG(p.t) OVER (ORDER BY p.seq)) / 1000.0 AS gap_s
    FROM walk_point AS p
    JOIN local_walk AS w ON w.id = p.walk_id
  )
  SELECT seq, gap_s FROM gaps
  WHERE seq > <before-lock-seq> AND seq <= <after-unlock-seq>
  ORDER BY seq;

  WITH gaps AS (
    SELECT p.seq,
           (p.t - LAG(p.t) OVER (ORDER BY p.seq)) / 1000.0 AS gap_s
    FROM walk_point AS p
    JOIN local_walk AS w ON w.id = p.walk_id
  )
  SELECT COUNT(*) AS new_points, AVG(gap_s) AS average_gap_s,
         MAX(gap_s) AS maximum_gap_s
  FROM gaps
  WHERE seq > <before-lock-seq> AND seq <= <after-unlock-seq>;
  ```

  Record only the query's counts, sequences and gaps. Compare the gaps
  with the requested sampling interval of about three seconds. State
  whether they support continued delivery across the locked interval.
  Record zero new points honestly; do not substitute a simulator result.
- [ ] OWNER — Stop tracking with `await tracker.stop()` in the retained
  harness, or the live screen's finish flow if that task is available.
  Confirm the service or foreground watcher stops. Stopping the tracker
  preserves `local_walk` and its points for recovery/finish; do not erase
  an unfinished walk as part of this check. Remove the owner-local harness.
