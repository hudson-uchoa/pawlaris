## R1 — minor — the matrix cannot hold two rows for one route            FIXED

**Where:** `services/api/tests/security/matrix.py:15-29`, `:67-75`;
`services/api/tests/security/test_role_matrix.py:21-23`
**Spec:** `04` §5; `08` P2-5 Build, as made precise with this review
**Problem:** `PERMISSION_MATRIX` is a dictionary keyed by `(method, path)`,
and the role test sends the request to that key. Both are enough for the
three routes that exist and neither survives the rest of the table:

1. **Several rows share a route.** `POST /tasks` is rows 11 and 12;
   `PATCH /tasks/{id}` is rows 13, 14 and 15; `POST /walks/{id}/finish` is
   rows 18 and 19. A dictionary keeps one case per route, so a leader-only
   case such as row 15 would have nowhere to go.
2. **Routes with a path parameter.** The key of `PATCH /pets/{id}` is its
   template, and the request must go to a real id. The builder returns a body
   and headers only.

The task's wording, "one entry per row", was loose — row 2 alone names five
routes — and that was the spec's doing. It is cheaper to fix the shape now
than in each of the ten tasks that add rows.
**Fix:** as `08` P2-5 now states: `PERMISSION_MATRIX` is a list of cases,
each with its row number, method, route template, expected status per role,
and a builder that returns the concrete URL with the body and headers.
Several cases may name the same route. The census takes a route as named when
any case has its method and template. One test proves the shape: two cases
for one probe route, one of them with a path parameter, are both run by RB-1.

FIXED in ab3c6b4. The matrix is a list of cases with route templates and
concrete request URLs. The new RB-1 shape regression failed on the old
dictionary and now runs both parameterized-route cases for both roles.
No application code changed. The security gate passes (54 tests), and
`pnpm verify --allow-pending` reports 14 pass, 0 fail, 0 pending.

## Assumptions and questions

- The census reads routes through `fastapi.routing.iter_route_contexts`,
  because the installed FastAPI resolves included routers lazily. Accepted;
  if a later FastAPI renames it, the census fails loudly, which is the safe
  direction.
- Authentication is recognised by the presence of `current_user` in a
  route's dependency tree. A second way of authenticating would be reported
  as unauthenticated until it is built on `current_user` — accepted.
