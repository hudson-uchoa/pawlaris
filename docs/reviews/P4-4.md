## R1 — major — offline, both forms are dead and the network message never shows   OPEN

**Where:** `apps/mobile/src/features/auth/LoginScreen.tsx:62,112`;
`RedeemScreen.tsx:58,122`; `apps/mobile/app/(auth)/login.tsx`,
`redeem.tsx` (`online={connection.status !== 'offline'}`)
**Spec:** `09` §2.1 (network → "Sem conexão. O primeiro acesso precisa
de internet.")
**Problem:** both screens take an `online` input, return early from
`submit` and disable their submit buttons when it is false. The routes
feed it from the engine's status. On a phone with no network, the
first-ever login is exactly the case `09` §2.1's network message exists
for. Here it shows a disabled **Entrar** with no explanation instead,
and the message appears only when the engine believes it is online but
the request fails. The spec says nothing about disabling either form
offline; "Online only" and "disabled offline" in `09` are reserved for
Settings actions.

The input was added in `2827b52`. The orchestrator's stage instruction
then had the routes wire it from the engine (`0cf8656`), so the
direction was wrong too.

None of the 25 cases sets `online` to false, so five mutants survived:
the two guards and the two routes' wiring.
**Fix:** remove `online` from `AuthScreenProps`, both screens and both
routes. Submitting always sends the request, and a transport failure
shows `strings.auth.networkError`, as the existing R5.1 case already
asserts. In `__tests__/shell.test.tsx`, add a case: with NetInfo
offline, the login route's **Entrar** is enabled, and pressing it with
a failing fake `Http` shows the network message.

## R2 — minor — the reserve login's request is never checked          OPEN

**Where:** `apps/mobile/src/features/auth/__tests__/LoginScreen.test.tsx:224`
**Spec:** `09` §2.1 and `11` §4.5 (on the reserve, the email is filled
in and not editable)
**Problem:** the RS-9 cases assert the locked field and the arrival.
Neither checks the request body. Sending the typed email (the empty
state) instead of the preserved one survives (`reserve sends the typed
email`). On the phone that would make every reserve re-login fail.
**Fix:** in the same-user reserve case, assert that the one
`/auth/login` request's body is `{ email: <preserved email>, password }`.

## R3 — minor — Retry-After rounding is untested                       OPEN

**Where:** `apps/mobile/src/features/auth/__tests__/LoginScreen.test.tsx:70`
**Spec:** `09` §2.1 ("Tente de novo em N min." from `Retry-After`)
**Problem:** the only valid header is `120`, a whole number of minutes,
so `Math.floor` survives in place of `Math.ceil`. With `Retry-After: 61`
the message would then say 1 min while the server refuses for 2.
**Fix:** add a row with `Retry-After: '61'` → `rateLimited(2)`.

## R4 — minor — the redeem discard sheet is untested                   OPEN

**Where:** `apps/mobile/src/features/auth/__tests__/RedeemScreen.test.tsx`
**Spec:** `09` §2.1, `10` §8.1 (Q-41)
**Problem:** redeeming always creates a different user, so with a
non-empty outbox the Q-41 sheet is the normal path. `RedeemScreen` has
its own copy of the sheet and its decision. No redeem case reaches it,
and a dismissal that confirms survives (`dismissing the sheet
confirms`).
**Fix:** mirror login's SE-3 `confirm`/`close` cases on redeem. Close
adopts nothing and keeps the outbox and the replica. Confirm wipes and
adopts.
