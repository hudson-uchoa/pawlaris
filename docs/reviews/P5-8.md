## R1 — blocker — the push task is never registered   FIXED in cb92be5
**Where:** apps/mobile/src/notifications/backgroundTask.ts:82
**Spec:** 09 §9.4, 08 P5-8
**Problem:** `defineTask` only defines the task. `expo-notifications`
calls it only after `Notifications.registerTaskAsync(PUSH_TASK)`, which
nothing calls, so no data-only message ever reaches the handler.
**Fix:** add `registerTaskAsync` to `NotificationsPort`, and call it at
module scope right after `defineTask`, catching a rejection, so absent
Firebase configuration stays quiet. Extend `__tests__/entry.test.ts`
to assert it runs for `pawlaris.push` before the router loads.

## R2 — blocker — the handler reads a payload that does not exist   FIXED in 9e8db9a
**Where:** apps/mobile/src/notifications/backgroundTask.ts:28, __tests__/push.test.ts
**Spec:** 09 §9.4, 04 §15
**Problem:** the task receives `NotificationTaskPayload`:
`{ notification, data: { dataString } }` (`RemoteMessageSerializer` in
the library), or a `NotificationResponse` after a tap. The handler
reads `body.data.type` directly, so every real message is ignored. The
tests feed the same invented shape, so they pass.
**Fix:** parse `body.data.data.dataString` as JSON, treating a missing
or malformed string as nothing to do, and ignore a payload with
`actionIdentifier`. Change every test to the library's shape, typed
with `NotificationTaskPayload`. Add cases for a malformed `dataString`
and for a tap payload.

## R3 — minor — quiet failure is untested, and one parse can throw   FIXED in 780c5b2
**Where:** apps/mobile/src/notifications/backgroundTask.ts:33, __tests__/push.test.ts
**Spec:** 09 §9.4, 04 §15
**Problem:**
- No test covers a token that cannot be obtained, or a failed `PUT`.
- `JSON.parse` of `session_user` is outside a `try`, so a damaged value
  throws inside the background task.
**Fix:** add both tests: nothing is recorded, and the next call
retries. Guard the parse. `04` §15 never sends an author to that
person, so the own-action check is defence only; keep it, using the
`author_id` the task's test names, and drop `actor_id`, which nothing
sends.

## R4 — major — the app imports the task's module-scope effects   FIXED in 3607100
**Where:** apps/mobile/src/bootstrap.ts:46, apps/mobile/src/notifications/backgroundTask.ts:95
**Spec:** 09 §9.4, 05 §3 (entry file)
**Problem:** `bootstrap.ts` imports `registerPushToken` from the module
that runs `defineTask` and `registerTaskAsync` on load. So the runtime
pulls those effects in, and a synchronous throw there, which the
`.catch` does not cover, stops the app from loading. The verify shows
it: `walksRoute.test.tsx` fails to run with `registerTaskAsync is not a
function`.
**Fix:**
- Move `registerPushToken` and its types to a new
  `notifications/pushToken.ts`, so only `index.ts` imports
  `backgroundTask.ts`.
- Make the module-scope call unable to throw, by also catching a
  synchronous failure.
- Add a test that a synchronous throw from `registerTaskAsync` does not
  escape the module.

## R5 — minor — the own-action test cannot fail   FIXED in 8168e92
**Where:** apps/mobile/src/notifications/__tests__/push.test.ts
**Spec:** 08 P5-8

**Fix:** give it a `together` template in the replica, with the same id
