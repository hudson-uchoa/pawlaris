## R1 — blocker — the push task is never registered            OPEN
**Where:** apps/mobile/src/notifications/backgroundTask.ts:82
**Spec:** 09 §9.4, 08 P5-8
**Problem:** `defineTask` only defines the task. `expo-notifications`
calls it only after `Notifications.registerTaskAsync(PUSH_TASK)`, which
nothing calls, so no data-only message ever reaches the handler.
**Fix:** add `registerTaskAsync` to `NotificationsPort`, and call it at
module scope right after `defineTask`, catching a rejection, so absent
Firebase configuration stays quiet. Extend `__tests__/entry.test.ts`
to assert it runs for `pawlaris.push` before the router loads.

## R2 — blocker — the handler reads a payload that does not exist            OPEN
**Where:** apps/mobile/src/notifications/backgroundTask.ts:28, __tests__/push.test.ts
**Spec:** 09 §9.4, 04 §15
**Problem:** the task receives `NotificationTaskPayload`:
`{ notification, data: { dataString } }` (`RemoteMessageSerializer` in
the library), or a `NotificationResponse` after a tap. The handler
reads `body.data.type` directly, so every real message is ignored. The
tests feed the same invented shape, so they pass.
**Fix:** parse `body.data.data.dataString` as JSON, treating a missing
or malformed string as nothing to do, and ignore a payload with
`actionIdentifier`. Change every test to the library's shape, typed
with `NotificationTaskPayload`. Add cases for a malformed `dataString`
and for a tap payload.
