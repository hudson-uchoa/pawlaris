## R1 — minor — a cancellation is swallowed when the password is wrong   OPEN

FIXED in afdea07.

**Where:** `services/api/app/security/passwords.py:17-25`, `:32-36`
**Spec:** `05` §2.1 (CPU-bound work leaves the event loop); `08` P2-2 Build
as extended with this review
**Problem:** when a caller is cancelled, `_run` waits for the thread and then
calls `worker.result()`. If the thread failed — a wrong password raises
`VerifyMismatchError` — that exception replaces the `CancelledError`, and
`verify_password` turns it into `False`. Observed:

| Call, cancelled while the thread runs | Result |
|---|---|
| verify with the right password | raises `CancelledError` |
| verify with a wrong password | returns `False`; the task is not cancelled |
| verify with a wrong password inside `asyncio.timeout` | no `TimeoutError`; returns `False` |

A cancelled coroutine that returns normally breaks every timeout and task
group around it.
**Fix:** after the thread ends, take its exception without raising it
(`worker.exception()` when the worker was not itself cancelled) and re-raise
the cancellation. A test cancels a verification of a wrong password while its
thread runs and expects `CancelledError`, and the same inside
`asyncio.timeout` expects `TimeoutError`; the slot is still held until the
thread ends.

## R2 — minor — the token helpers read the configuration on every call   OPEN

FIXED in e4f4dd4.

**Where:** `services/api/app/security/tokens.py:26-29`, `:47-50`
**Spec:** `08` P2-2 Build, as corrected with this review
**Problem:** `settings` is optional and defaults to `Settings()`. A caller
that leaves it out gets a new `Settings` per call: the `.env` file is read
and parsed on every request that decodes a token, on the event loop, and the
key comes from the environment instead of from the settings the application
was created with — a test application built with its own settings would sign
with one key and verify with another. The spec's signature gave the helpers
no way to receive the key; that was the spec's gap.
**Fix:** `settings` is a required argument: `issue_access(user, clock,
settings)` and `decode_access(token, clock, settings)`. Nothing in `app/`
constructs `Settings()` outside `create_app` and the CLI.

## R3 — minor — a bootstrap test that can hang, and a timezone never checked   OPEN

FIXED in d833c0b.

**Where:** `services/api/tests/auth/test_bootstrap.py:36-46`, `:51`
**Spec:** `08` P2-2 Tests, as extended with this review
**Problem:**

1. **The suite can wait forever.** The tests run the CLI as a subprocess with
   its passwords in the environment. With the variables numbered from 0
   instead of 1 the CLI finds none and asks at the console, and the test
   waits for a person. The reviewer's run stopped there for an hour and a
   half.
2. **The timezone given is not checked.** The test passes
   `America/Sao_Paulo`, which is also the column's default, so a bootstrap
   that ignores `--timezone` passes.

**Fix:** one commit of tests: the subprocess is awaited with a timeout, so a
CLI that waits for input fails the test instead of blocking it; the family is
created with a timezone other than the default and the stored value is
asserted.
