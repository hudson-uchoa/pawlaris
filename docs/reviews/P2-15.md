## R1 — minor — only one test file is kept away from the network     OPEN

**Where:** `services/api/tests/api/test_push.py` (`forbid_network`),
`services/api/tests/conftest.py` (`settings`)
**Spec:** `07` §5.1, as extended with this review
**Problem:** the fixture that fails a test when the HTTP client's real
transport is used lives in the push tests alone. Every other test builds
the app with push enabled and the real `ExpoPushSender`. Today none of them
registers a device, so none sends anything; the first one that does — a
completion test that also stores a push token — would post to Expo from a
test run.
**Fix:** move the guard to `conftest.py`, autouse, for every test; drop the
copy in `test_push.py`. Prove it: a test that makes a real client request
fails with the guard's message.

## R2 — minor — two things the push log gets wrong                   OPEN

**Where:** `services/api/app/push.py` (`ExpoPushSender._send`),
`services/api/app/main.py` (logging setup)
**Spec:** `05` §7 and `04` §15, as extended with this review
**Problem:** (a) the HTTP client logs every request at `INFO` through its
own logger — `HTTP Request: POST https://exp.host/… "HTTP/1.1 200 OK"` —
and the root logger prints it: a line that is not JSON, once per batch,
among logs that are one JSON object per line. (b) A ticket that Expo
refuses for a reason other than `DeviceNotRegistered` (`MessageRateExceeded`,
`MessageTooBig`, `InvalidCredentials`) is dropped without a word: the push
was not delivered and nothing says so.
**Fix:** (a) set the `httpx` logger to `WARNING` where logging is
configured. (b) After a batch, if any ticket has another error, write one
`ERROR` JSON line for the batch naming the distinct error codes and how
many tickets had each — never a token, a title or a body — and keep the
tokens. Tests in R3.

## R3 — minor — rules that no test holds                             OPEN

**Where:** `services/api/tests/api/test_push.py`
**Spec:** `07` §5.2 (the push row), as extended with this review
**Problem:** four mutants survive. (a) Deleting the token on any ticket
error: the only error ticket tested is `DeviceNotRegistered`. (b) Not
logging an Expo failure: the tests of an HTTP error and a timeout check
what the log must not contain and never that a line exists. (c, d) Pushing
again when a completion, or a walk start, arrives a second time under a new
`Idempotency-Key`: the replay tests reuse the key.
**Fix:** tests only, with the two of R2. (a) A `MessageRateExceeded` ticket
keeps its token and writes one `ERROR` JSON line with the code and no
token. (b) An HTTP error, a timeout and a body that is not tickets each
write exactly one `ERROR` JSON line, with the request's id when a request
caused the send. (c, d) The same completion body and the same walk-start
body under a new key answer `200` with the same row and send nothing. And
for R2a: no record from the `httpx` logger below `WARNING` during a send.

## Assumptions and questions

- Q-20, Q-21 and Q-22 are answered in `spec/QUESTIONS.md`: the token is
  opaque, 1 to 255 characters; a finish that creates a walk announces
  nothing; the duplicate push carries the winner's completion, the walk
  push its walk and pet.
- When Expo fails on one batch the batches after it are not attempted.
  Accepted: a family's event fits in one batch many times over.
- A client is opened for each send when none is injected. Accepted: a
  handful of sends a day; nothing to keep open or to close at shutdown.
- A push still running when the server stops is lost. Accepted: R3.43, push
  is an enhancement and the state arrives by sync.
- `POST /walks` looks the walk up before the shared create helper does the
  same, to know whether the row is new. Accepted: one more short query on a
  route used a few times a day.
