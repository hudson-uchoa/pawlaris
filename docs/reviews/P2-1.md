## R1 — minor — three behaviours are implemented but not tested         OPEN

**Where:** `services/api/tests/db/test_constraints.py`,
`services/api/tests/db/test_migrations.py`
**Spec:** `08` P2-1 Tests, as extended with this review; `03` §5 (the live
index), §4.2 (the key format), §1.3 (the epoch)
**Problem:** the migration is right in each of these, and a wrong one passes
every test:

1. **Two pets, one occurrence.** With the live index on `(task_id,
   occurrence_key)` alone, a `per_pet` occurrence could be completed for one
   pet only. The test tries a second row for the *same* pet and never a row
   for another pet.
2. **A key with seconds.** `2026-09-14T08:00:00` is not an occurrence key;
   a pattern that accepts it passes.
3. **The epoch is random.** A migration that writes the same `sync_epoch` in
   every database passes, and two restored servers would look like one
   history to a phone.

**Fix:** one commit of tests, no change to the migration: live completions
for two different pets of one occurrence are both accepted; a key with
seconds is rejected on completions and on timers; two scratch databases have
different epochs. Confirm each by making the mistake it guards against and
watching the test fail.

## Assumptions and questions

- The migration is `0002`, on top of the empty baseline `0001` of P0-4,
  rather than "a single initial migration" as `03` §11 puts it — accepted;
  `0001` was merged with P0 and a migration is never edited after merge.
- `tests/conftest.py` now builds its database through the helpers of
  `tests/factories.py` — accepted; one way of creating a scratch database is
  better than two, and the other API tests still pass.
- `downgrade()` drops the `citext` extension, which `upgrade()` creates only
  if absent. On a database that already had it for another purpose the
  downgrade would remove it. Left as it is: the database is this
  application's alone.
