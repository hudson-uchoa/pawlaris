## R1 — major — the hook loops on a built value                      FIXED

**Where:** `apps/mobile/src/replica/useReplica.tsx`; `selectors.ts`
**Spec:** `10` §2.4 and RP-4, written with this review
**Problem:** `useReplica` hands the selector straight to Zustand, which asks
it for a snapshot more than once per render and expects the same object for
the same state. `selectPets`, `selectMembers`, `selectTemplates`,
`selectWalks`, `selectCompletionsForRange` and `selectDayView` build a new
array or view each time, so the first screen to use one of them with the
hook cannot render (probe 1). The hook's tests select a string.
**Fix:** `10` §2.4. The hook computes the selector once for each state it
sees, again only when the selector changes, and returns the value it last
returned when the new one is shallowly equal (`zustand/shallow` has the
comparison). Tests: RP-4, in `useReplica.test.tsx`.

FIXED in 31ab663. The hook keeps the state, the selector and the value it
last returned, and gives that value back for the same pair or for a
shallowly equal result. Six RP-4 cases. Probe 1 again: both components
render once, and a change to another slice does not re-render the list.

## R2 — major — a cold start pays per row twice over                 FIXED

**Where:** `apps/mobile/src/replica/apply.ts` — `completionCutoff`,
`queueRecord`, `withRow`, `hydrateReplica`
**Spec:** `10` §2.2 and §2.3 as made explicit with this review; the second
pillar — `hydrate()` runs before the first render
**Problem:** two costs that grow with the replica where one read would do.
(a) The cutoff reads and parses the family row once for every completion,
in `hydrate` — where the query has already left the old ones out — and in
every applied page: 3 602 statements to start an app that holds 3 600
completions. (b) Each row is its own state update that copies its whole
slice and the pending map, so building a slice of n rows copies n²/2
entries. Under Node the two together make `hydrate` take 2.6 s for a
family's four months (probe 2); the phone is slower, and nothing is on
screen meanwhile.
**Fix:** read the cutoff once per outermost transaction. Build the next
state by copying each slice that changed once, at the flush, and `hydrate`
by filling each slice once. Test: `hydrate` issues the same number of SQL
statements for ten rows as for a thousand. The reviewer measures the rest
again in the second pass.

FIXED in f8051c6. The cutoff is read once per outermost transaction and
forgotten when it ends; a batch is a list of operations applied to one
copy of each slice it touches; `hydrate` hands over its rows as one
operation. Probe 2 again, same replica: the eight pages take 0.43 s, down
from 3.2 s; `hydrate` takes 0.19 s, down from 2.6 s, with 2 statements.

## R3 — minor — the apply module replaces a method of its driver     FIXED

**Where:** `apps/mobile/src/replica/apply.ts`, `coordinateTransactions`
**Spec:** `10` §1 — the seams are injected and substituted by tests; the
driver's `onTransactionEnd`, written with this review
**Problem:** to learn that an outer transaction committed, the module
assigns its own function to `driver.transaction` and keeps a second depth
counter beside the driver's. It works while nothing else touches that
property. A test that spies on it and restores it — as the crash tests of
the next tasks will — takes the hook away without a sound: the row is on
disk and the store never hears of it (probe 3).
**Fix:** `SqlDriver` gains `onTransactionEnd(listener)` (`10` §1), in
`db/driver.ts` and in `testing/memoryDriver.ts`, with its cases in
`db/__tests__/driver.test.ts` for both drivers: called once per outermost
transaction, `true` after a commit and `false` after a rollback, never for
an inner call. `apply.ts` subscribes to it and replaces nothing. This
changes two files of P3-1, by the spec's decision.

FIXED in 4d27b4d. Both drivers call their listeners after the commit or the
rollback of the outermost transaction; five cases run against each.
`apply.ts` subscribes once for each store and driver, and nothing assigns
to the driver any more. Probe 3 again: the store follows the disk.

## What the spec got wrong (the orchestrator's)

- **`10` §2 named the hook and said nothing of its contract.** That a
  selector may build a value, and what the hook then owes React, is §2.4 and
  RP-4 now.
- **`10` §1 gave no way to hear a commit**, while §2.3 asked `apply.ts` to
  act on one made by somebody else's transaction. The implementer had to
  invent one; the seam has it now.
- **`10` §2.2 did not say what `hydrate` may cost**, though it runs before
  the first frame.
- **`10` §2.3 did not say which generation and which server's cursor** a
  write uses outside `arrive` (`004c221`, before the task started).
