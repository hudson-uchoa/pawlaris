## R1 — major — simultaneous logins pass the limit of five               OPEN

FIXED in 3473f8f. Attempts reserve distinct slots before verification;
internal failures and cancellation release them. The regression first
returned 20 unauthorized responses, then passed with five 401s and fifteen
429s. Cancellation and internal failure checks also pass.

**Where:** `services/api/app/security/ratelimit.py:14-31`;
`services/api/app/services/auth.py:27`, `:52`
**Spec:** `02` R1.5; `04` §3 and `07` §5.2 as extended with this review
**Problem:** `check` looks at the failures already recorded, and a failure is
recorded only after the password has been verified. Requests that arrive
together all pass `check` before any of them has failed. Observed against the
running application: 20 wrong passwords for one email sent at once → 20
answers of `401`, none of `429`; the right password sent next → `429` for 15
minutes. The limit of 5 is then the global cap of 30, and the account's owner
is the one locked out.
**Fix:** count the attempt when it starts, as `04` §3 now states: `check`
reserves a place in the email's window, so attempts in flight count against
the limit; a success clears the email's counter as today; an attempt that
ends in neither a success nor `invalid_credentials` — an internal error, a
cancelled request — gives its place back. Test, written first and seen to
fail: 20 simultaneous wrong passwords for one email → exactly 5 answers of
`401` and 15 of `429`.

## R2 — minor — a failure in an auth route is logged without its cause   OPEN

FIXED in a0d1b2b. Auth failures log the exception type and frame locations
without messages, source lines or local values. The new diagnostic test
first failed on the suppression placeholder; confidentiality checks pass.

**Where:** `services/api/app/main.py:66-72`
**Spec:** `05` §7 "No error is silent", as extended with this review; `05` §5
**Problem:** for `/auth/*` and `/me/password` the `exc` field is the fixed
text "Authentication exception details suppressed." A database that is down
during a refresh leaves a `500` in the log with no exception type and no
location. Keeping credentials out of the log is right; the message of an
exception can hold them, its type and its stack frames cannot.
**Fix:** for those paths `exc` carries the exception's type and its stack
frames — file, line and function — and never its message or local values.
The confidentiality tests stay as they are; one more asserts the type and a
frame are present.

## R3 — minor — three behaviours are implemented but not tested          OPEN

FIXED in 8d41992. Tests cover the unknown account's single hash,
success resetting mixed-case counters, and both Retry-After orderings.
No application code changed for this finding.

Review gates: `uv run --directory services/api pytest tests/auth -q`:

**Where:** `services/api/tests/auth/test_login.py`,
`services/api/tests/auth/test_rate_limit.py`
**Spec:** `08` P2-3 Tests and `07` §5.2, as extended with this review
**Problem:** the code is right in each of these, and removing it leaves every
test green:

1. **An unknown email costs one hashing operation.** Without it the answer
   for an unknown email comes back sooner than for a wrong password, which is
   what R1.5 forbids.
2. **A success clears the counter whatever the letter case of the email.**
   The reset is tried with the same spelling only.
3. **`Retry-After` is the longer wait** when the email's limit and the global
   cap both apply.

**Fix:** one commit of tests, no change to the code: a login with an unknown
email runs exactly one password hash; after failures, a success with the
email in another letter case clears them; with both limits reached,
`Retry-After` is the larger of the two.
