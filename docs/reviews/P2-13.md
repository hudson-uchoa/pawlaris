## R1 — major — the family lock is held while the body arrives      FIXED

**Where:** `services/api/app/services/assets.py` (`upload_asset`, `write`)
**Spec:** `04` §13, `03` §1.2 and `05` §2.1, as corrected with this review
**Problem:** the upload takes the family lock first and then reads the
request body, inside the same transaction. The phone's network paces that
read. For as long as it lasts — seconds on a good connection, minutes on a
bad or stalled one — no other write of the family can proceed: the other
phone's completions, walks and edits all wait on the server. Seen with a
probe: while the second chunk was pending, another session could not take
the family's lock. The implementation followed the spec, which said only
"the family lock comes first"; the spec was wrong for the one route whose
body arrives slowly, and now says so.
**Fix:** read, hash, compare and validate with no lock and outside
`transactional`; only then open the transaction: take the family lock, read
the actor again (RB-3), look the id up, move the file, insert the row. The
cleanup of the temporary and stored files stays as it is. Tests, per `07`
§5.2: while a chunk is pending another session takes the family lock at
once; an actor removed while the body arrives gets `401` and no file is
left. The role-matrix test must keep passing unchanged.

FIXED in 7721aca.

The length checks, the read into the temporary file, the hash and the
validation now run before `transactional`; the transaction holds only the
lock, the actor read again, the lookup, the move and the insert. Two tests
were added: with the body paused after its first chunk another session
takes the family lock with `NOWAIT`; an actor removed while the body is
paused gets `401` with the assets, the revision and the files as before.
Both failed on the earlier code. No existing test changed, and the
role-matrix test passes as it was. Checked by the reviewer: the diff, the
138 asset cases and the full harness.

## R2 — minor — every parser Pillow has may read the upload          FIXED

**Where:** `services/api/app/services/assets.py` (`validate_image`)
**Spec:** `04` §13 (Validation), as corrected with this review
**Problem:** `Image.open(path)` tries every format plugin until one accepts
the bytes, and only then is the format compared with the three accepted
ones. Bytes from the network should never reach parsers the app has no use
for.
**Fix:** `Image.open(path, formats=("JPEG", "PNG", "WEBP"))`. The existing
cases keep their meaning: another format is then unidentified → `422`.

difference from outside — another format was `422` before and is `422`
now — so none was added; the mutant that adds GIF to the accepted table now
survives because Pillow no longer identifies a GIF at all.
