## R1 — major — a validation error is a sentence, not a field and a code  FIXED

FIXED in `e175fe1`. Both validators return `{field, code}` errors using the
codes from Q-7, and report independent problems together. Every rejection
asserts its full error objects. The strengthened tests first produced 90
assertion failures against the sentence errors, then passed. All 362 shared
tests passed with 100% line and branch coverage after this fix.

**Where:** `packages/shared/src/recurrence.ts:23-24` and every `errors:` in
the two validators; `packages/shared/src/recurrence.test.ts:65-72, 98-102`
**Spec:** `08` P1-2 Build and the answer to Q-7; `08` P1-7 (`{field, code}[]`)
**Problem:** both validators return `errors: string[]` of English sentences.
That was the assumption of Q-7, asked properly and confined to one place; the
answer is different. The app shows Portuguese and marks the field at fault,
so it needs to know which field and why, not to match on wording — the reason
P1-7 already gives the form validators `{field, code}[]`.
**Fix:** `errors` is `{field: string, code: string}[]`. Fields: `freq`,
`interval`, `byday`, `bymonthday`, `date`, `starts_on`, `times_of_day`, or an
unknown key's own name. Codes: `required`, `invalid`, `out_of_range`,
`duplicate`, `unsorted`, `too_many`, `mismatch`, `unknown_key`. Each rejection
test asserts the `field` and `code` it expects instead of "a non-empty
string"; that is also what makes the rejections tell one cause from another.
Report every problem found, not only the first, where that is cheap.
