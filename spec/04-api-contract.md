# 04 — API Contract

Base: `https://<host>/api/v1`. Socket: `wss://<host>/api/v1/ws`.
JSON everywhere except the asset upload (the raw image as the request body)
and the asset file download (image bytes).

**This file is the contract.** `spec/contracts/openapi.json` is generated from
the FastAPI app and committed; `pnpm contract-check` fails on any drift.
TypeScript types are generated from that file, so a backend change that breaks
the client breaks `tsc`.

The API has **one read path** — `GET /sync` — and a set of mutations. There are
no per-resource list endpoints: the phone reads its replica *(ADR-019, ADR-020)*.

---

## 1. Conventions

| Rule | Detail |
|---|---|
| Ids | UUIDv4, lowercase, generated by the client for every row it creates |
| Time | ISO-8601 UTC with `Z` (`2026-09-14T10:30:00Z`). Dates are `YYYY-MM-DD` |
| Auth | `Authorization: Bearer <access_token>` on everything except §3's public routes and `/health` |
| Idempotency | Every mutation marked ⟳ requires `Idempotency-Key: <uuidv4>` *(ADR-021)*. Missing or malformed → 400 `idempotency_key_required` |
| Bodies | Unknown fields are rejected (`extra = "forbid"`) → 422. So is any string that contains the character U+0000, which the database cannot store, and any integer outside the range of its column (`sort_order`: −2 147 483 648 to 2 147 483 647). A number that is not finite — `NaN`, `Infinity`, `-Infinity`, which a lenient JSON parser lets through — is `422` too. The checks for U+0000 and for non-finite numbers are written once, in the same place, and cover every request body, at any depth |
| Responses | A mutation returns the full row it produced or changed, in the same shape `/sync` uses |
| Family | The family is always the caller's. No route takes a family id. A row of another family is `404`, never `403` |
| Timing | Every response carries `Server-Timing: app;dur=<milliseconds>` — the time from the request reaching the app to the response leaving it *(R5.9)* |
| Compression | Responses over 1 KB are gzip-compressed when the client sends `Accept-Encoding: gzip` |

### 1.1 Errors

RFC 7807, `Content-Type: application/problem+json`:

```jsonc
{ "type": "about:blank", "title": "Forbidden", "status": 403,
  "code": "forbidden", "detail": "Only a leader may archive a pet." }
```

`code` is the stable, machine-readable part. `title` and `detail` are English
and are for logs and developers; the app never shows them — it maps `code` to
a Portuguese message of its own.

| Status | `code` | When |
|---|---|---|
| 400 | `idempotency_key_required` | ⟳ route without a valid key |
| 401 | `invalid_credentials` | wrong email or password |
| 401 | `token_invalid` | access or refresh token missing, malformed, expired, revoked |
| 403 | `forbidden` | role not allowed (§5) |
| 404 | `not_found` | no such row in the caller's family; unknown route |
| 409 | `last_leader` | would leave the family without a leader |
| 409 | `email_taken` | redeem with an email already registered |
| 409 | `asset_conflict` | upload of an existing asset id with different bytes |
| 410 | `invite_invalid` | invite unknown, expired or used |
| 413 | `payload_too_large` | upload over 8 MiB (8 388 608 bytes) |
| 422 | `idempotency_key_reused` | the key was already used by another family or for another kind of row |
| 422 | `validation_error` | body failed validation; `errors: [{loc, msg}]` included |
| 429 | `rate_limited` | login throttled; `Retry-After` header set |
| 500 | `internal_error` | an unhandled server error, including a commit that fails; `detail` is a fixed sentence and says nothing about the failure |
| any other | the status name in lower snake case, e.g. 405 `method_not_allowed` | an error raised by the framework itself |

How the phone treats each status is in `10-client-sync.md` §4.

### 1.2 Rules common to every mutation

These hold for §8–§12 without being repeated there.

| Situation | Result |
|---|---|
| Create with an `id` that already exists in the caller's family (different idempotency key) | `200` with the existing row; nothing changes |
| `PATCH`, or an action such as `archive`, `undo`, `cancel`, `finish`, on a row that does not exist in the caller's family | `404` |
| `PATCH` on a soft-deleted row | `404` |
| `DELETE` on a row already soft-deleted | `200` with the tombstone, unchanged — deletes are idempotent, like undo and cancel |
| A **scalar** reference in the body (`pet_id`, `task_id`, `assigned_to`, `replaces_task_id`) that names no row of the caller's family | `404` |
| An **element of a list** (`pet_ids`) that names no row of the caller's family | `422` |
| Soft references (`avatar_asset_id`, `attachment_asset_id`, `photo_asset_id`) | never checked *(AS-1)* |

Every numeric column is a JSON number in responses, never a string
(`weight_kg`, `distance_m`). Decimals in requests are validated to the column's
scale: `weight_kg` is 0.01–119.99 with at most two decimals, otherwise `422`.

Every mutation takes the family lock before it checks or writes anything
*(03 §1.2)*, and commits before its response is produced *(05 §2.1)*.

## 3. Auth

```
POST /auth/login     {email, password}                         -> Session
POST /auth/refresh   {refresh_token}                           -> Session
POST /auth/logout    {refresh_token}                           -> 204
POST /auth/redeem    {code, email, password, display_name}     -> Session
GET  /me                                                       -> Me
PATCH /me            {display_name}                            -> Me
POST /me/password    {current_password, new_password}          -> 204
PUT  /me/push-token  {token}                                   -> 204
DELETE /me/push-token {token}                                  -> 204
```

```jsonc
// Session
{ "access_token": "<jwt>", "refresh_token": "<opaque>",
  "access_expires_at": "2026-09-14T10:45:00Z", "user": Me }

// Me
{ "id", "email", "display_name", "role", "color", "family_id" }
```

- **Access token:** JWT, HS256, claims `sub` (user id), `fam` (family id),
  `role`, `exp`, `iat`. Lifetime 15 min. The role claim is a hint for the UI;
  the server re-reads the user row on every request, so a demotion or a
  disabled account takes effect immediately.
- **Refresh token:** 32 random bytes, base64url. Stored server-side only as
  SHA-256. Lifetime 30 days from issue.
- **`/auth/login`:** verifies the password; creates a new chain. A disabled
  account answers `401 invalid_credentials`. Rate limit per R1.5: an in-memory
  counter keyed by lowercase email, 5 failures in a sliding 15 minutes → `429`
  until the window frees a slot; a success clears the counter. **An attempt is
  counted when it starts**, so attempts in flight count against the limit: of
  20 simultaneous wrong passwords for one email, 5 are checked and 15 get
  `429`. An attempt that ends in neither a success nor `invalid_credentials`
  — an internal error, a cancelled request — gives its place back.
- **`/auth/refresh`** *(R1.8)*:

  | Presented token | Result |
  |---|---|
  | unknown, expired, or `revoked_at` set | `401 token_invalid` |
  | valid, not rotated | mark `rotated_at = now`; issue a successor in the same chain; `200` |
  | rotated, and none of the tokens issued from it (`parent_id` = this token) has been rotated | issue **another** successor in the same chain; `200` |
  | rotated, and a token issued from it has been rotated | set `revoked_at` on every token of the chain, **commit**, then `401 token_invalid` |

  The last row is the one place a `401` must not roll back: the revocation is
  committed before the error is returned.

- **`/auth/logout`:** revokes the chain of the presented token. Always `204`,
  even for an unknown token. It does not touch push devices; the client calls
  `DELETE /me/push-token` first.
- **`/auth/redeem`:** consumes an invite *(R1.3)*, in one transaction. The
  claim is one atomic statement — `UPDATE invite_code SET used_at = :now WHERE
  code = :code AND used_at IS NULL AND expires_at > :now RETURNING family_id,
  role` — and no row back means `410 invite_invalid`, so two simultaneous
  redeems of one code cannot both succeed. Then, under the family lock, it
  creates the user in the invite's family with the invite's role, sets the
  invite's `used_by` to that user, and returns a session. `used_by` is
  written last because it references the user row, which does not exist at the
  claim *(Q-14)*. If anything after the claim fails — `409 email_taken`, for
  one — the transaction rolls back and the invite is unused again. The
  password is hashed after the claim and before the family lock: an invalid
  code costs no hash, and the family is never locked while one runs. Password
  rules: 8–128 characters, no other constraint. The email is 3–254 characters
  with no whitespace and an `@` that is neither its first nor its last
  character, and is not in `pawlaris.invalid`, the domain that removal writes
  (§4); anything else is `422`, refused before the claim.
- Password hashing and verification run off the event loop
  (`asyncio.to_thread`) behind a semaphore of 2, so a burst of logins can
  neither freeze the single worker nor exhaust its memory. The rate limiter's
  map holds at most 10 000 emails (oldest evicted), and logins as a whole are
  capped at 30 per minute → `429`.
- **`/me/password`:** wrong current password → `401 invalid_credentials`. On
  success, stores the new hash, revokes **every** refresh chain of the user and
  returns `204`. The calling app then logs in again with the new password
  without showing the login screen; other devices are signed out *(R1.12)*.
- The routes in this section, and `POST /invites`, are online-only. They never
  go through the outbox and take no `Idempotency-Key`. The UI disables their
  buttons while offline.
- **`PUT /me/push-token`:** upsert by token; re-points the token to the caller.
  `token` is an opaque string of 1–255 characters, stored and sent to Expo as
  received: no prefix or pattern is checked *(Q-20)*; outside those bounds →
  `422`.
- **`DELETE /me/push-token`:** deletes the row only if the token is the
  caller's. An unknown token, or one that belongs to someone else, deletes
  nothing and is still `204`.
- There is no `/auth/register`. Gate: `POST /auth/register` → 404 *(R1.1)*.

## 4. Family

```
PATCH  /family                     {name?, timezone?}   ⟳  -> Family   leader
POST   /invites                    {role}                  -> Invite   leader
PATCH  /family/members/{user_id}   {role}               ⟳  -> Member   leader
DELETE /family/members/{user_id}                        ⟳  -> Member   leader
```

```jsonc
// Invite
{ "code": "7K2M9QX4TB", "role": "member", "expires_at": "2026-09-15T10:30:00Z" }
```

- `timezone` must be a valid IANA name (`zoneinfo.ZoneInfo(tz)` succeeds).
- `PATCH` role: the resulting state must keep one enabled leader, else
  `409 last_leader` *(FM-1)*. The check is on the result, not on who acts, so a
  sole leader cannot demote themselves.
- `DELETE` member *(R1.20)*, in one transaction: `409 last_leader` if they are
  the last enabled leader; else set `disabled_at`, replace their email with
  `removed+<user_id>@pawlaris.invalid` (so the address can be invited again),
  revoke all their refresh chains, delete their push devices, and set
  `assigned_to = NULL` on every template assigned to them. Returns the member
  row. A user may remove themselves under the same rule. Removing an
  already-disabled member returns the row unchanged; `PATCH` on one is `404`.
- Family and member rows reach phones through `/sync`.

## 5. Permissions

The role check lives in the API *(R1.18)*. **Reads are family-wide** *(R1.19)*;
every row below is a write.

"Own task" = a template whose `created_by` is the caller.
"Own walk" = a walk whose `user_id` is the caller.

| # | Route | Member | Leader |
|---|---|---|---|
| 1 | `GET /sync` | 200 | 200 |
| 2 | `GET /me`, `PATCH /me`, `POST /me/password`, `PUT/DELETE /me/push-token` | 200/204 | 200/204 |
| 3 | `PATCH /family` | 403 | 200 |
| 4 | `POST /invites` | 403 | 200 |
| 5 | `PATCH /family/members/{id}` | 403 | 200 |
| 6 | `DELETE /family/members/{id}` | 403 | 200 |
| 7 | `POST /pets`, `PATCH /pets/{id}` | 200 | 200 |
| 8 | `POST /pets/{id}/archive`, `/unarchive` | 403 | 200 |
| 9 | `POST /weights`, `DELETE /weights/{id}` | 200 | 200 |
| 10 | `POST /health-events`, `PATCH`, `DELETE /health-events/{id}` | 200 | 200 |
| 11 | `POST /tasks` with `assigned_to` ∈ {self, null} | 200 | 200 |
| 12 | `POST /tasks` with `assigned_to` = someone else — except a fork, see below | 403 | 200 |
| 13 | `PATCH /tasks/{id}`, `DELETE /tasks/{id}` — own task | 200 | 200 |
| 14 | `PATCH /tasks/{id}`, `DELETE /tasks/{id}` — someone else's task | 403 | 200 |
| 15 | `PATCH /tasks/{id}` setting `assigned_to` to someone else — own task | 403 | 200 |
| 16 | `POST /completions`, `POST /completions/{id}/undo` — any task | 200 | 200 |
| 17 | `POST /timers`, `POST /timers/{id}/cancel` — any timer | 200 | 200 |
| 18 | `POST /walks`, `POST /walks/{id}/finish` — own walk | 200 | 200 |
| 19 | `POST /walks/{id}/finish`, `/discard` — someone else's walk | 403 | 200 |
| 20 | `POST /walks/{id}/discard` — own walk | 200 | 200 |
| 21 | `GET /walks/{id}/route` | 200 | 200 |
| 22 | `PUT /assets/{id}`, `GET /assets/{id}/file` | 201/200 | 201/200 |

Row 16 is deliberate: anyone may complete or undo anyone's occurrence, and
`completed_by` / `undone_by` record who actually did it. Refusing would make the
record wrong.

**The fork exception to row 12.** A member may create a template assigned to
someone else when it is a fork of their own template that already had that
assignee: `replaces_task_id` names a template they created, and the new
`assigned_to` equals that template's `assigned_to`. Without this, a member
editing the schedule of their own task — one a leader had assigned to another
person — would end the old template and fail to create its successor.

> **RB-1** A parametrized test walks every row of this table for both roles and
> asserts the status.
>
> **RB-2** A member calling each leader-only route gets `403` — not `200`, and
> not an accidental `404`. Includes row 15.
>
> **RB-3** The role and the enabled state that decide a mutation are the ones
> read after the family lock is taken, not the ones the request arrived with
> *(`03` §1.2)*. The idempotency wrapper reads the actor again once it holds
> the lock and hands that row to the handler; the few writers that do not use
> the wrapper do the same themselves. Gate: one test walks the matrix — in
> every case where a member is `403`, a leader demoted while their request
> waits for the lock gets `403`; in every mutation case, an actor removed
> while their request waits gets `401`; neither writes anything.
>
> **Route census.** A test enumerates the app's routes at runtime. Each HTTP
> route must be on the public allowlist (`/health`, `/auth/login`,
> `/auth/refresh`, `/auth/logout`, `/auth/redeem`) **or** require
> authentication **and** be named in a row of this table. A new route with no
> row fails the census. The app serves no documentation routes
> (`docs_url`, `redoc_url` and `openapi_url` are all off; the contract is
> exported by a script). Exactly one WebSocket route exists, `/ws`; it
> authenticates in-band and is covered by WS-2.

## 6. Sync

```
GET /sync?since=<revision>&limit=<1..1000, default 500>
```

```jsonc
{
  "epoch": "6f1c…",         // server_meta.sync_epoch (03 §1.3)
  "revision": 10432,        // the cursor to store: see below
  "has_more": false,        // true -> call again with since = revision
  "server_time": "2026-09-14T10:30:00Z",
  "changes": [              // ascending by revision, across all entities
    { "entity": "pets",             "row": { /* Pet */ } },
    { "entity": "task_completions", "row": { /* Completion */ } }
  ]
}
```

Entity names: `family`, `members`, `pets`, `weight_entries`, `health_events`,
`task_templates`, `task_completions`, `task_timers`, `walk_sessions`, `assets`.

- Returns every row of the caller's family with `revision > since`, across all
  ten entities, merged and ordered by revision, cut at `limit`.
- `since=0` is the full snapshot.
- Soft-deleted rows are included with `deleted_at` set; the client applies them.
- A row changed between two pages simply shows up again later with a higher
  revision. The cursor is monotonic; nothing is lost.

**The upper bound.** The ten entity queries are separate statements, each with
its own snapshot. Without a bound, a transaction that commits between two of
them can put a higher revision in the response than a row the earlier query
missed — and the phone's cursor would pass that row forever. So:

```
hi = SELECT value FROM family_revision WHERE family_id = :f      -- first, once (0 if no row)
for each entity:
    SELECT … WHERE family_id = :f AND revision > :since AND revision <= :hi
    ORDER BY revision LIMIT :limit + 1
merge the ten lists by revision; keep the first `limit`
has_more = more remained
revision = has_more ? the last kept row's revision : hi
```

Because revisions are commit-ordered *(03 §1.1)*, every row with
`revision <= hi` was committed before `hi` was read and is visible to every
later statement. Returning `hi` as the cursor when the page is the last one
also keeps the phone's cursor equal to the family's revision, so a poke for a
revision it already has triggers nothing.

**Epoch.** The phone stores `epoch` beside its cursor. If a response's `epoch`
differs from the stored one, the phone discards its synced rows, sets the
cursor to 0 and pulls again *(10 §5)*.

> **SY-2** Mutate 5 rows of different entities; `/sync?since=<before>` returns
> exactly those 5, ascending by revision, nothing else.
>
> **SY-4** With 12 changed rows and `limit=5`, three calls following
> `has_more` return 5, 5, 2 rows with no duplicate and no omission.
>
> **SY-5** A second family's rows never appear, whatever `since` is.
>
> **SY-6** The cursor never passes an unseen row. Gate: call the service with an
> explicit `hi` lower than the newest rows → none of them is returned and
> `revision` equals `hi`; a following call with the real `hi` returns them.

## 7. Realtime *(ADR-019)*

```
WSS /ws
```

The socket carries no data. It tells a phone that the family's revision moved.

```jsonc
// client -> server, first frame, within 5 s of connecting
{ "type": "auth", "access_token": "<jwt>" }

// server -> client, after a valid auth
{ "type": "ready", "revision": 10432 }

// server -> client, after every committed transaction that bumped the revision
{ "type": "poke", "revision": 10433 }

// keepalive — the pong repeats the family's current revision
{ "type": "ping" }   ->   { "type": "pong", "revision": 10433 }
```

| Close code | Meaning |
|---|---|
| 4401 | no valid `auth` frame, or the access token expired — refresh and reconnect |
| 4408 | no `auth` frame within 5 s |

- The token travels in a frame, never in the URL, so it reaches no access log.
- The first frame must be the `auth` frame. Any other first frame closes with
  4401, whatever else it carries — a token in a `ping` frame authenticates
  nobody.
- Frames are tiny, and the server says so: Uvicorn is started with
  `--ws-max-size 4096`, so a longer frame closes the socket instead of being
  buffered. Its default would let a client that never authenticates make
  the server hold 16 MiB per connection.
- A socket leaves the hub the moment it closes, dies or expires. A socket
  that fails while a poke is being delivered is removed, and the poke goes
  on to the family's other sockets.
- The server closes the socket with 4401 when the token's `exp` passes.
- `poke.revision` is the family revision after the commit. Pokes are sent after
  commit, to every socket of that family, including the author's.
- Pokes may arrive out of order or be dropped. The client's only reaction to
  `ready`, `poke` or `pong` is: *if `revision > last_revision`, pull*. The
  30-second ping therefore doubles as a safety net for a poke that was lost on
  an open socket.
- On a valid `auth` frame the server **registers the socket in the hub first**,
  then reads the family revision, then sends `ready`. In the other order a
  commit between the read and the registration would be neither in `ready` nor
  poked.
- Token expiry is checked against the injected `Clock` on every inbound frame
  and before every outbound frame, and by a sweep every `WS_SWEEP_SECONDS`
  (default 30). The auth timeout is `WS_AUTH_TIMEOUT_SECONDS` (default 5). Both
  are settings so tests can shorten them.

> **WS-1** A phone that misses any number of pokes converges on the next pull.
> Gate: connect, drop the socket, mutate out of band, reconnect → the client
> reaches the server's revision with no user action.
>
> **WS-2** A socket that never authenticates is closed with 4408; one that
> authenticates with another family's token never receives this family's pokes.

## 8. Pets

```
POST  /pets                 PetCreate            ⟳ -> Pet
PATCH /pets/{id}            PetPatch             ⟳ -> Pet
POST  /pets/{id}/archive                         ⟳ -> Pet      leader
POST  /pets/{id}/unarchive                       ⟳ -> Pet      leader

POST   /weights             {id, pet_id, weight_kg, measured_at, note?}   ⟳ -> WeightEntry
DELETE /weights/{id}                                                      ⟳ -> WeightEntry

POST   /health-events       HealthEventCreate    ⟳ -> HealthEvent
PATCH  /health-events/{id}  HealthEventPatch     ⟳ -> HealthEvent
DELETE /health-events/{id}                       ⟳ -> HealthEvent
```

```jsonc
// PetCreate — id, name, species required
{ "id", "name", "species", "sex"?, "breed"?, "color"?, "birthdate"?,
  "microchip_id"?, "avatar_asset_id"?, "notes"?, "sort_order"? }
// PetPatch — any subset of PetCreate except id and species

// HealthEventCreate — id, pet_id, type, title, occurred_at required
{ "id", "pet_id", "type", "title", "notes"?, "occurred_at", "next_due_on"?,
  "attachment_asset_id"? }
// HealthEventPatch — any subset except id and pet_id
```

- `DELETE` is a soft delete and returns the tombstoned row with `200`.
- A `POST` whose `id` already exists in the family (different idempotency key)
  returns the existing row with `200` and changes nothing. In another family →
  `404`.
- `PATCH` sets only the fields present. An explicit `null` clears a nullable
  field. Last writer wins, per field *(R5.7)*.
- `PATCH` on a soft-deleted row → `404`. `DELETE` on one → `200` with the
  tombstone, unchanged *(§1.2, Q-15)*.

## 9. Tasks

```
POST   /tasks        TaskCreate   ⟳ -> TaskTemplate
PATCH  /tasks/{id}   TaskPatch    ⟳ -> TaskTemplate
DELETE /tasks/{id}                ⟳ -> TaskTemplate
```

```jsonc
// TaskCreate
{
  "id": "uuid",
  "title": "Remédio da Aurora",
  "description": null,
  "category": "medication",
  "assigned_to": "uuid-duda",          // null = anyone
  "requires_photo": false,
  "timer_seconds": null,
  "reminder_class": "critical",
  "sort_order": 0,
  "recurrence": { "freq": "daily", "interval": 1 },
  "times_of_day": ["08:00", "20:00"],
  "starts_on": "2026-09-01",
  "pet_ids": ["uuid-aurora"],
  "completion_mode": "per_pet",
  "ends_on": null,
  "replaces_task_id": null             // set when this template is a fork (R3.8)
}

// TaskPatch — any subset of:
{ "title", "description", "category", "assigned_to", "requires_photo",
  "timer_seconds", "reminder_class", "sort_order", "ends_on" }
```

- `TaskCreate` validation: the recurrence rules of `03` §4.1; every `pet_ids`
  entry is a pet of the family, no duplicates; `assigned_to` is a member of the
  family or null; `replaces_task_id`, when set, names a template of the family.
- An `assigned_to` that names a **removed** member — one with `disabled_at`
  set — is read as null, on `POST` and on `PATCH`, and stored as null. It is
  not an error: the task is kept, for anyone *(ADR-037)*. The reading happens
  before the assignment rules of §5 are applied, so the request is judged as
  one that assigns to nobody. An `assigned_to` that names no member of the
  family is `404`, as §1.2 says.
- `TaskPatch` does not contain schedule fields. Sending one is an unknown field
  → `422` *(TK-1)*.
- `ends_on` may be any date or null. A value earlier than `starts_on` is valid
  and means the template has no occurrences.
- Assignment rules *(R3.3)* are rows 11–15 of §5.
- A fork is two independent mutations sent by the client, **in this order**: a
  `POST` creating the new template, then a `PATCH` setting `ends_on` on the old
  one. If the second fails for good, the family sees two templates — visible
  and fixable — instead of a task that silently stopped. The server has no fork
  endpoint; its only knowledge of forks is `replaces_task_id` and the exception
  to permission row 12 *(§5)*.

> **No route returns occurrences.** The server never evaluates a recurrence
> rule. Gate: no route path contains `occurrence`, `today` or `schedule`.

## 10. Completions

```
POST /completions              CompletionCreate   ⟳ -> Completion   (200)
POST /completions/{id}/undo                       ⟳ -> Completion   (200)
```

```jsonc
// CompletionCreate
{
  "id": "uuid",
  "task_id": "uuid",
  "occurrence_key": "2026-09-14T08:00",
  "pet_id": "uuid-aurora",            // null when the template is 'together'
  "completed_at": "2026-09-14T11:02:31Z",
  "photo_asset_id": null,             // may name an asset not uploaded yet (AS-1)
  "note": null
}
```

The server sets `completed_by` (the caller), `title_snapshot` (the template's
current title) and clamps `completed_at` to at most five minutes ahead of its
own clock. The write path is fixed by `03` §5.

| Situation | Response |
|---|---|
| New completion | `200`, the created row |
| Same `Idempotency-Key` again | `200`, the same row, nothing written |
| Another live completion already holds this `(task, occurrence, pet)` | `200`, **the winning row** — its `id` differs from the one sent |
| `photo_asset_id` not uploaded yet | `200`, accepted |
| Template soft-deleted or ended | `200`, accepted — history is preserved |
| `per_pet` without a pet, or with a pet not in the template; `together` with a pet | `422` |
| Unknown `task_id` | `404` |
| An `id` that belongs to a completion of another family | `404`, and nothing of that row |
| Undo of a live completion | `200`, row with `undone_at` / `undone_by` set |
| Undo of an already-undone completion | `200`, row unchanged |

After committing a **created** completion the server queues the family-activity
push *(R3.39)*. After a **lost** one where the loser is not the winner, it
queues the duplicate push to the winner *(R3.41)*. A failed push never fails
the request.

Gates: `CP-1` … `CP-5` in `03` §5.

## 12. Walks

```
POST /walks                {id, pet_id, started_at}        ⟳ -> Walk
POST /walks/{id}/finish    WalkFinish                      ⟳ -> Walk
POST /walks/{id}/discard                                   ⟳ -> Walk
GET  /walks/{id}/route                                       -> { "points": [[lat,lon,t,acc],...] }
```

```jsonc
// WalkFinish
{
  "pet_id": "uuid", "started_at": "...",       // repeated so finish can create the walk
  "ended_at": "...", "paused_ms": 0,
  "distance_m": 2140.5, "duration_s": 1830, "avg_pace_s_per_km": 855,
  "note": null,
  "route": [[-23.5505, -46.6333, 1757845351000, 6.5], ...],  // already filtered and simplified
  "preview": [[-23.5505, -46.6333], ...]                     // the same line reduced to ≤ 32 points
}
```

- `POST /walks` creates an `active` walk owned by the caller. It triggers the
  walk-started push *(R3.42)*.
- `finish` is an upsert: if the walk does not exist it is created from the body
  (the start mutation may have been lost), then set to `finished`, and the
  route stored in `walk_route`. `point_count` and `has_route` come from `route`.
  Finishing an already finished walk returns it unchanged.
- `discard` sets `status = 'discarded'` and `deleted_at`. Discarding an
  already-discarded walk returns it unchanged; `finish` on a discarded walk
  returns it unchanged (it stays discarded); `discard` of a walk the server
  never saw is `404`.
- Limits: `preview` at most 32 points; `route` at most 5 000 points; `distance_m` 0–200 000; `duration_s`
  0–86 400. Beyond → `422`.
- `GET …/route` returns `404` when `has_route` is false.
- There is no "one active walk" check on the server *(ADR-029)*.

## 13. Assets

```
PUT /assets/{id}?kind=<asset_kind>      body: the image bytes      -> Asset   (201, or 200 if it already exists)
    Content-Length: <bytes>             required
    X-Content-SHA256: <hex>             required
GET /assets/{id}/file                                              -> image bytes
```

The upload is the raw file as the request body — not multipart. That keeps the
handler in control of every byte it reads.

- The client picks `id` before uploading, so a completion can reference the
  photo first *(AS-1)*.
- **Order of work, fixed:** authenticate → reject a missing or over-limit
  `Content-Length` (`413`) → read `request.stream()` chunk by chunk into a
  temporary file, hashing as it goes and aborting with `413` the moment the
  count passes 8 MiB (8 388 608 bytes; that many are accepted, one more is
  not) → compare the hash with `X-Content-SHA256` (`422` on
  mismatch) → validate the image → take the family lock and read the actor
  again *(RB-3)* → look the `id` up → move the file into storage → insert the
  row. Nothing is read before authentication, and nothing is buffered in memory.
- **No lock is held while the body arrives.** The phone's network paces the
  upload, and a connection that stalls half way may stay open for a long time:
  a family lock held across it would stop every other write of the family
  until it dies. So the lock is taken only once the body is on disk, hashed
  and validated, and everything after it is local and short.
- **Validation is on content, not on the client's claims.** Open with Pillow
  restricted to the three accepted formats (`formats=("JPEG", "PNG", "WEBP")`,
  so no other parser ever sees the bytes; opening reads only the header), take
  format and size from it: format must be JPEG, PNG or WebP; width and height
  1–4 096; then `verify()`. Never fully decode the image. Anything else →
  `422`. The stored MIME comes from the detected format; the request's
  `Content-Type` is ignored.
- Idempotent by `id`: same id and same hash → `200` with the existing row;
  same id, different hash → `409 asset_conflict`. An id that maintenance has
  swept stays swept: the same bytes get `200` with the row and its
  `deleted_at`, and no file is stored again.
- The route is declared with a raw `Request`; its body is documented in the
  OpenAPI schema through `openapi_extra` (binary `application/octet-stream`).
- `GET …/file` requires auth, streams the file from storage with the stored
  MIME and `Cache-Control: private, max-age=31536000, immutable`. Unknown or
  deleted → `404`.
- There is no delete route. Unreferenced assets are swept by maintenance *(AS-2)*.

## 15. Push messages *(R3.39–R3.43)*

Sent by the server to Expo's push API (`https://exp.host/--/api/v2/push/send`)
after commit, from a background task. Each event sends **two** messages per
target device:

```jsonc
// 1. visible — shown by the OS even if the app is dead
{ "to": "<token>", "channelId": "family-activity", "priority": "high",
  "title": "Duda", "body": "concluiu \"Remédio da Aurora\" às 07:12",
  "data": { "type": "completion", "task_id": "...", "occurrence_key": "...",
            "pet_id": null, "completion_id": "..." } }

// 2. data-only — wakes the app's background task so it can cancel the local reminder
{ "to": "<token>", "priority": "high",
  "data": { "type": "completion", "silent": true, "task_id": "...",
            "occurrence_key": "...", "pet_id": null, "completion_id": "..." } }
```

| `data.type` | Targets | Title / body |
|---|---|---|
| `completion` | every enabled member except the author | `<Autor>` / `concluiu "<título>" às HH:mm` — for `per_pet`, `concluiu "<título>" (<pet>) às HH:mm` |
| `completion_duplicate` | the winner only | `<Perdedor>` / `também marcou "<título>"` |
| `walk_started` | every enabled member except the walker | `<Autor>` / `saiu para passear com <pet>` |

The exact templates are in `09-screens.md` §10.

`completion_duplicate` and `walk_started` send only the visible message.
Their `data` *(Q-22)*:

```jsonc
{ "type": "completion_duplicate", "task_id": "...", "occurrence_key": "...",
  "pet_id": null, "completion_id": "<the winner's>" }
{ "type": "walk_started", "walk_id": "...", "pet_id": "..." }
```

When the winner and the loser of a race are the same person nothing is sent
*(R3.39: nobody is told about their own action)*. Only `POST /walks` sends
`walk_started`: a `finish` that creates the walk, because its start never
arrived, sends nothing *(Q-21)*. An undo, a replayed request and a finished
or discarded walk send nothing.

`HH:mm` is `completed_at` in the family timezone. A token Expo reports as
`DeviceNotRegistered` is deleted from `push_device`.

## 16. Contract governance

1. The orchestrator changes this file.
2. The implementer changes the FastAPI schemas to match.
3. `pnpm contract-freeze` regenerates `spec/contracts/openapi.json`.
4. `pnpm types` regenerates `packages/shared/src/api-types.ts`.
5. `tsc` breaks at every client call site that no longer matches.

`pnpm contract-check` fails on any difference between the running app's schema
and the committed file, so steps 3–4 cannot be forgotten.
